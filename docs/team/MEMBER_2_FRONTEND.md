# Member 2 - Frontend Workstream

## Mission

Build an optional demonstration dashboard that makes the GridWise pipeline easy to understand during rehearsal and video recording. It is not part of the organizer's judged API and must never be required to call the backend.

## Owned files

- `frontend/**`
- `frontend/README.md`
- Frontend-only tests and assets

Do not change backend schemas or endpoint behavior. Raise contract issues to Member 1.

## Product scope

Create a lightweight responsive interface with:

- configurable backend base URL;
- health/readiness indicator;
- scenario ID input;
- 1-3 operator-note inputs;
- editable 24-hour demand, solar, and tariff table;
- battery parameter form;
- load-one-public-sample action;
- submit/loading/timeout/error states;
- directive interpretation cards showing note index, applicability, type, adjustment, and explanation;
- 24-hour result table;
- demand, solar-used, grid-import, tariff, and battery-energy visualization;
- totals for grid energy, cost, and peak grid import;
- plan summary;
- JSON request/response inspector with copy/download controls;
- clear disclaimer that schedules are generated by the backend and the UI is not the judge endpoint.

## Boundaries

- Never interpret operator notes in the browser.
- Never calculate or repair the optimized schedule in the browser.
- Never embed provider credentials.
- Never silently change outgoing numbers, hours, note order, or field names.
- Never require frontend availability for `/health` or `/optimize-energy`.
- Keep sample data sourced from the public JSON pack; do not hard-code expected schedules as application logic.

## UX requirements

- Validate obvious client-side shape errors without replacing backend validation.
- Display controlled 400, 422, 500, network, and timeout errors safely.
- Preserve decimal values and hour order.
- Make all 24 hours usable on laptop screens.
- Include accessible labels, keyboard navigation, readable contrast, and meaningful chart legends.
- Make the architecture flow visible enough to support the three-minute video.

## Frontend acceptance criteria

- Builds and tests from a clean environment.
- Works against a mock API and the actual local backend.
- Loads at least one organizer public sample accurately.
- Sends the exact request schema and renders the exact response schema.
- Handles slow, malformed, and failed API responses without crashing.
- Contains no secrets or model-provider calls.
- Can be deployed separately or omitted without affecting judging.

## Handoff

Provide Member 3 with the frontend build command, output directory, runtime API-base configuration, and hosting needs. Provide Member 4 with mock fixtures and the UI acceptance checklist.
